# Chapter 30 — A2A deep dive

> **A2A (Agent2Agent)** is an open protocol for agents built by different teams, vendors and
> frameworks to **discover each other and collaborate on tasks** — without exposing their
> internal prompts, tools or memory. MCP gives one agent depth (tools); A2A gives your system
> reach (other agents).

**You will learn:** the A2A model (Agent Cards, messages, parts, tasks, artifacts, contexts),
task states and multi-turn flows, the operations (send, stream, get, list, cancel, subscribe,
push notifications), the three protocol bindings (JSON-RPC, gRPC, HTTP+JSON), versioning,
security and signed Agent Cards, multi-tenancy, A2A vs MCP vs plain function calls, and how to
build a minimal A2A agent and client from the spec.

**Where this fits:** builds on multi-agent systems (Ch 25 — A2A is message passing across
organizational boundaries), JSON-RPC and identity specs (Ch 28) and MCP (Ch 29). Agent discovery
at scale is the agent registry (Ch 31); securing agent-to-agent traffic is Ch 36.

> **Verified against:** the A2A specification repository — v1.0.0 (released 2026-03-12) and
> v1.0.1 (2026-05-26): `docs/specification.md`, `specification/a2a.proto`, CHANGELOG. The server
> and client below were built from the spec and run. For production, use an official SDK
> (`a2a-sdk` for Python was at 1.2.x in October 2026) and the spec's conformance details.

## 1. The idea in plain words

Inside one application, agents can call each other as functions or tools (Ch 25, 27). But when
the other agent belongs to **another team, company or vendor**, you need a contract:

- How do I **find** it and learn what it can do? → its **Agent Card**
- How do I **ask** it something and get results back? → **messages** and **tasks** with **artifacts**
- What if it takes an hour, or needs more information from me? → **task states**, streaming,
  push notifications, `input-required`
- How do we **trust** each other? → standard HTTP auth declared in the card, **signed** cards

A2A agents are **opaque**: you see their declared skills and their outputs, never their internals.
That's the point — it lets organizations collaborate without sharing their code, data or prompts.

---

## 2. Analogy

**Hiring a specialist firm through its public profile.** You read their profile (Agent Card:
services, how to contact them, credentials required), send a work order (message), get a job
number (task ID), receive status updates ("working", "need more info from you"), and finally the
deliverables (artifacts). You never see how they organize their staff internally.

## 3. How it works

### 3.1 The core objects

| Object | What it is | Key fields (v1.0 JSON names) |
|---|---|---|
| **Agent Card** | Public self-description for discovery | `name`, `description`, `version`, `supportedInterfaces` (`url`, `protocolBinding`, `protocolVersion`), `capabilities` (`streaming`, `pushNotifications`, `extendedAgentCard`), `securitySchemes`, `securityRequirements`, `defaultInputModes/OutputModes`, `skills`, `signatures` |
| **Skill** | One thing the agent can do | `id`, `name`, `description`, `tags`, `examples`, input/output modes |
| **Message** | One turn of communication | `messageId`, `role` (`ROLE_USER` / `ROLE_AGENT`), `parts`, optional `taskId`, `contextId`, `referenceTaskIds` |
| **Part** | A piece of content | exactly one of `text`, `raw` (bytes), `url`, `data` (JSON); plus `mediaType`, `filename` |
| **Task** | The unit of work with a lifecycle | `id`, `contextId`, `status` (`state`, optional `message`, `timestamp`), `artifacts`, `history` |
| **Artifact** | A deliverable produced by the task | `artifactId`, `name`, `parts` |
| **Context** | `contextId` groups related tasks and messages (like a conversation) | — |

Discovery: clients fetch `https://{domain}/.well-known/agent-card.json`, query a **registry/catalog**
(Ch 31), or use a configured card URL. Authenticated clients can fetch an **extended Agent Card**
with more details.

### 3.2 Task states

```
             ┌──────────────► TASK_STATE_COMPLETED   (terminal)
SUBMITTED ─► WORKING ─┼─────► TASK_STATE_FAILED      (terminal)
                      ├─────► TASK_STATE_CANCELED    (terminal)
                      ├─────► TASK_STATE_REJECTED    (terminal: the agent declined)
                      ├─────► TASK_STATE_INPUT_REQUIRED  (paused: needs more info from the client)
                      └─────► TASK_STATE_AUTH_REQUIRED   (paused: needs additional authorization)
```

**Multi-turn:** when a task is `INPUT_REQUIRED`, the client sends another message with the **same
`taskId`** (and `contextId`) to continue it — exactly the human-in-the-loop idea from Ch 26, between
agents.

### 3.3 Operations and bindings

v1.0 defines the operations once and maps them to three bindings:

| Operation | JSON-RPC method | REST endpoint |
|---|---|---|
| Send message | `SendMessage` | `POST /message:send` |
| Send message, stream updates (SSE) | `SendStreamingMessage` | `POST /message:stream` |
| Get task | `GetTask` | `GET /tasks/{id}` |
| List tasks | `ListTasks` | `GET /tasks` |
| Cancel task | `CancelTask` | `POST /tasks/{id}:cancel` |
| Subscribe to a task's updates | `SubscribeToTask` | `POST /tasks/{id}:subscribe` |
| Push-notification configs (create/get/list/delete) | `CreateTaskPushNotificationConfig`, … | `/tasks/{id}/pushNotificationConfigs` |
| Extended Agent Card | `GetExtendedAgentCard` | `GET /extendedAgentCard` |

The gRPC binding uses the same names. (Code written for the pre-1.0 drafts used method names like
`message/send`; v1.0 also aligned enums to ProtoJSON style such as `TASK_STATE_COMPLETED` and
`ROLE_USER`.)

**Getting updates** for long tasks: **poll** (`GetTask`), **stream** (SSE via
`SendStreamingMessage`/`SubscribeToTask`), or **push notifications** (the agent calls your webhook) —
for tasks that run for hours or clients that disconnect.

### 3.4 Versioning and errors

- Clients send an `A2A-Version` header (e.g. `1.0`) on every request; an **empty header is treated
  as 0.3** for backward compatibility. An agent that doesn't support the version returns
  `VersionNotSupportedError`.
- Standard errors map to JSON-RPC codes: `TaskNotFoundError` −32001, `TaskNotCancelableError` −32002,
  `PushNotificationNotSupportedError` −32003, `UnsupportedOperationError` −32004,
  `ContentTypeNotSupportedError` −32005, `InvalidAgentResponseError` −32006,
  `ExtendedAgentCardNotConfiguredError` −32007, `ExtensionSupportRequiredError` −32008,
  `VersionNotSupportedError` −32009.
- v1.0 added native **multi-tenancy** (a `tenant` field on requests) and **extensions** (declared
  URIs, negotiated via the `A2A-Extensions` header).

### 3.5 Security and trust

- **Transport security:** HTTPS; production agents authenticate callers with standard schemes
  declared in the card (OAuth 2.0 / OIDC, API keys, mTLS). v1.0 removed legacy OAuth flows
  (implicit, password) and supports PKCE and device-code flows.
- **Signed Agent Cards:** cards can carry **JWS signatures** over a **JCS-canonicalized** card, so a
  client can verify the card wasn't tampered with and comes from the claimed provider. Rejecting
  unsigned or badly-signed cards is what stops **agent spoofing / shadowing** in registries (Ch 31).
- **In-task authorization:** `AUTH_REQUIRED` lets an agent pause until extra credentials/consent are
  provided.
- **Treat everything another agent sends as untrusted data** — it can carry prompt injection (Ch 36).
  Apply least privilege to what a remote agent's output can trigger in your system.

### 3.6 A2A vs MCP vs function calls

| | Function call / agent-as-tool | MCP | A2A |
|---|---|---|---|
| Other side is | Code in your process | A tool/data server | An autonomous agent |
| Boundary | None | Process or network | **Organization / team / vendor** |
| Interaction | Call → return | Call tool → result | Task with lifecycle, multi-turn, artifacts, streaming |
| Duration | Milliseconds | Usually seconds | Seconds to days |
| Discovery | Import | Configured servers / MCP Registry | Agent Cards / registries |
| Use when | Same codebase | Giving an agent capabilities | Delegating work to someone else's agent |

They combine naturally: *your* agent uses MCP for its own tools and A2A to delegate to a partner's
agent, which in turn uses its own MCP servers.

### 4.1 A minimal A2A v1.0 agent (JSON-RPC binding)

```python
# a2a_server.py — a minimal A2A v1.0 agent (JSON-RPC binding) built from the spec, for learning
import re
import uuid
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

BASE_URL = "http://localhost:9000"
AGENT_CARD = {
    "name": "Acme Order Status Agent",
    "description": "Answers questions about the status of Acme Shoes orders.",
    "supportedInterfaces": [{"url": f"{BASE_URL}/a2a", "protocolBinding": "JSONRPC", "protocolVersion": "1.0"}],
    "provider": {"organization": "Acme Shoes", "url": "https://acme.example.com"},
    "version": "0.1.0",
    "capabilities": {"streaming": False, "pushNotifications": False},
    "defaultInputModes": ["text/plain"],
    "defaultOutputModes": ["text/plain"],
    "skills": [{"id": "order-status", "name": "Order status",
                "description": "Look up shipping status and ETA for an order ID like A-1043.",
                "tags": ["orders", "shipping"], "examples": ["Where is order A-1043?"]}],
}
ORDERS = {"A-1043": "shipped via DHL, ETA 2026-10-15"}
TASKS: dict[str, dict] = {}

app = FastAPI()

@app.get("/.well-known/agent-card.json")
def agent_card():
    return AGENT_CARD

def rpc_error(req_id, code, message):
    return JSONResponse({"jsonrpc": "2.0", "id": req_id, "error": {"code": code, "message": message}})

def agent_text(text):
    return {"messageId": str(uuid.uuid4()), "role": "ROLE_AGENT", "parts": [{"text": text}]}

def handle_message(msg):
    task = TASKS.get(msg.get("taskId")) if msg.get("taskId") else None
    if task is None:                                   # new task
        task = {"id": str(uuid.uuid4()), "contextId": msg.get("contextId") or str(uuid.uuid4()),
                "status": {"state": "TASK_STATE_SUBMITTED"}, "artifacts": [], "history": []}
        TASKS[task["id"]] = task
    task["history"].append(msg)
    text = " ".join(p.get("text", "") for p in msg["parts"])
    m = re.search(r"\bA-\d{4}\b", text)
    if not m:                                          # multi-turn: ask the caller for more input
        task["status"] = {"state": "TASK_STATE_INPUT_REQUIRED",
                          "message": agent_text("Which order ID? It looks like A-1043.")}
        return task
    status = ORDERS.get(m.group(0))
    if status is None:
        task["status"] = {"state": "TASK_STATE_FAILED", "message": agent_text(f"No order {m.group(0)}.")}
        return task
    task["artifacts"].append({"artifactId": str(uuid.uuid4()), "name": "order-status",
                              "parts": [{"text": f"Order {m.group(0)}: {status}"}]})
    task["status"] = {"state": "TASK_STATE_COMPLETED"}
    return task

@app.post("/a2a")
async def a2a(request: Request):
    body = await request.json()
    req_id, method, params = body.get("id"), body.get("method"), body.get("params", {})
    version = request.headers.get("A2A-Version", "0.3")   # spec: empty header is treated as 0.3
    if version != "1.0":
        return rpc_error(req_id, -32009, f"VersionNotSupportedError: this agent supports A2A 1.0, got {version}")
    if method == "SendMessage":
        return {"jsonrpc": "2.0", "id": req_id, "result": {"task": handle_message(params["message"])}}
    if method == "GetTask":
        task = TASKS.get(params.get("id"))
        if task is None:
            return rpc_error(req_id, -32001, "TaskNotFoundError")
        return {"jsonrpc": "2.0", "id": req_id, "result": task}
    if method == "CancelTask":
        task = TASKS.get(params.get("id"))
        if task is None:
            return rpc_error(req_id, -32001, "TaskNotFoundError")
        if task["status"]["state"] in ("TASK_STATE_COMPLETED", "TASK_STATE_FAILED", "TASK_STATE_CANCELED"):
            return rpc_error(req_id, -32002, "TaskNotCancelableError")
        task["status"] = {"state": "TASK_STATE_CANCELED"}
        return {"jsonrpc": "2.0", "id": req_id, "result": task}
    return rpc_error(req_id, -32601, f"Method not found: {method}")
```

Run it with `uvicorn a2a_server:app --port 9000`, then open
`http://localhost:9000/.well-known/agent-card.json`.

### 4.2 A client: discover, send, continue a multi-turn task, handle errors

```python
# a2a_client.py — discover an agent from its card, then talk to it over JSON-RPC
import uuid
import httpx

class A2AClient:
    def __init__(self, base_url, http=None):
        self.http = http or httpx.Client(base_url=base_url, timeout=30)
        card = self.http.get("/.well-known/agent-card.json").json()              # 1. discovery
        iface = next(i for i in card["supportedInterfaces"] if i["protocolBinding"] == "JSONRPC")
        self.card, self.endpoint = card, httpx.URL(iface["url"]).path              # 2. pick a binding

    def call(self, method, params):
        r = self.http.post(self.endpoint, headers={"A2A-Version": "1.0"},
                           json={"jsonrpc": "2.0", "id": str(uuid.uuid4()), "method": method, "params": params})
        body = r.json()
        if "error" in body:
            raise RuntimeError(body["error"])
        return body["result"]

    def send(self, text, task_id=None, context_id=None):
        msg = {"messageId": str(uuid.uuid4()), "role": "ROLE_USER", "parts": [{"text": text}]}
        if task_id:
            msg["taskId"] = task_id
        if context_id:
            msg["contextId"] = context_id
        return self.call("SendMessage", {"message": msg})["task"]

if __name__ == "__main__":
    from fastapi.testclient import TestClient
    from a2a_server import app
    client = A2AClient("http://testserver", http=TestClient(app))      # in-process; use a real URL in practice
    print("skills:", [s["id"] for s in client.card["skills"]])
    task = client.send("Where is my order?")
    print(task["status"]["state"], "->", task["status"]["message"]["parts"][0]["text"])
    task = client.send("It's A-1043", task_id=task["id"], context_id=task["contextId"])   # continue the SAME task
    print(task["status"]["state"], "->", task["artifacts"][0]["parts"][0]["text"])
    print("GetTask:", client.call("GetTask", {"id": task["id"]})["status"]["state"])
    try:
        client.call("CancelTask", {"id": task["id"]})
    except RuntimeError as e:
        print("cancel completed task:", e)
```

Verified output:

```
skills: ['order-status']
TASK_STATE_INPUT_REQUIRED -> Which order ID? It looks like A-1043.
TASK_STATE_COMPLETED -> Order A-1043: shipped via DHL, ETA 2026-10-15
GetTask: TASK_STATE_COMPLETED
cancel completed task: {'code': -32002, 'message': 'TaskNotCancelableError'}
```

And a request without the `A2A-Version: 1.0` header gets
`{"code": -32009, "message": "VersionNotSupportedError: ... got 0.3"}`.

What this teaching server leaves out (use an SDK for these): streaming over SSE, push
notifications, `ListTasks` pagination, authentication, signed cards, persistence of tasks, and
full validation of every field.

## 5. Production view

| Concern | Practice |
|---|---|
| Discovery | Publish signed Agent Cards; register them in your agent registry (Ch 31); cache cards per spec guidance |
| Long tasks | Persist tasks durably (Ch 26); support streaming and push notifications; set timeouts and cancellation |
| Auth | OAuth 2.0/OIDC with least-privilege scopes; per-tenant isolation; audit every task |
| Trust | Verify card signatures; allowlist partner agents; treat remote outputs as untrusted |
| Observability | Trace context across agent boundaries; log task IDs and states (Ch 34) |
| Versioning | Send `A2A-Version`; support the versions your partners use; follow the changelog |
| SLAs | Agree on latency, availability and error semantics with partner agent owners — it's a service contract |

## 6. Common mistakes

- Using A2A between agents in the same codebase (use function calls or agents-as-tools).
- Treating a remote agent's artifacts as trusted instructions.
- No persistence for tasks — a restart loses every in-flight task.
- Ignoring `INPUT_REQUIRED`/`AUTH_REQUIRED` and treating them as failures.
- Building against pre-1.0 method names and enum formats.
- Publishing unsigned cards in a shared registry.

## 7. Practice

**Level 1**
1. Run `a2a_client.py`. Then send a message about order `A-9999`. What state comes back?
2. Add a second skill ("return-policy") to the Agent Card and handle it in `handle_message`.

**Level 2**
3. Implement the REST binding for `SendMessage` (`POST /message:send`) next to the JSON-RPC one, sharing
   the same `handle_message` logic. Both must return identical tasks.
4. Make your Ch 14 agent an A2A **client**: give it a tool `ask_order_agent(question)` that discovers the
   order agent via its card and sends messages, continuing `INPUT_REQUIRED` tasks by asking the user.

**Level 3**
5. Sign the Agent Card: canonicalize it (sorted keys, no whitespace — a simplified JCS), sign with an
   Ed25519 key (e.g. `cryptography` package), publish the signature, and make the client **refuse**
   cards whose signature doesn't verify. Then tamper with the card's skills and show the client rejects it.

<details>
<summary>Answers</summary>

1. Name, description, version, provider, supported interfaces (URL + binding + protocol version),
   capabilities, security schemes/requirements, default input/output modes, skills, and optional
   signatures. Published at `/.well-known/agent-card.json` (or in registries/direct configuration).
2. Terminal: completed, failed, canceled, rejected. Paused: input-required, auth-required.
3. Send another message with the same `taskId` (and `contextId`) containing the requested information.
4. Polling (`GetTask`), streaming over SSE (`SendStreamingMessage`/`SubscribeToTask`), and push
   notifications to a webhook.
5. An empty header is treated as version 0.3, so the agent returns `VersionNotSupportedError` (−32009).
6. To let clients verify the card is authentic and unmodified — preventing spoofed or shadow agents
   from impersonating real ones in registries.
7. When the other side is an autonomous agent owned by another team/organization, with its own
   reasoning and potentially long, multi-turn tasks — rather than a tool/data source you call directly.
